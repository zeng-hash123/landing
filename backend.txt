I'm building the backend for an AI landing page generator targeting marketing agencies. 
I have a pre-built component library (HTML templates with {{token}} placeholders + 
metadata.json files per section type) already on disk. Build the Python backend that 
powers the core generation pipeline.

TECH STACK
- Python, FastAPI
- OpenAI SDK pointed at Kimi K2.7 (Moonshot AI), OpenAI-compatible endpoint:
  base_url = "https://api.moonshot.ai/v1"
  model = "kimi-k2.7"
- Jinja2 for template rendering
- Pydantic for data models/validation
- Supabase (Postgres) for persistence — use the `supabase-py` client
- Async throughout (asyncio.gather for parallel agent calls)

Each HTML file uses {{token}} placeholders matching the tokens list.

- Create a `supabase_client.py` module that initializes and exports a single

- Generate the SQL schema (as a .sql file I can run in the Supabase SQL editor) 
  for these tables:

  pages
    - id (uuid, primary key, default gen_random_uuid())
    - brief (jsonb) — stores the PageBrief
    - brand_kit (jsonb, nullable)
    - sections (jsonb) — list of SectionSelection objects
    - meta (jsonb) — meta_title, meta_description
    - flags (jsonb) — compliance flags
    - created_at (timestamptz, default now())
    - updated_at (timestamptz, default now())

  page_versions
    - id (uuid, primary key, default gen_random_uuid())
    - page_id (uuid, foreign key -> pages.id)
    - state (jsonb) — full snapshot of sections + brief + brand_kit at this version
    - html (text) — rendered HTML at this version
    - created_at (timestamptz, default now())

  Add an index on page_versions.page_id for fast version history lookups.

BUILD THE FOLLOWING MODULES:

1. `library.py` — Component library loader
   - `load_component_library(base_path: str) -> list[dict]`: scans all section folders, 
     reads each metadata.json, attaches the raw HTML template text to each entry, 
     returns a flat list of dicts (one per template file).
   - Load this once at app startup, store in memory (module-level or FastAPI app state) 
     — this stays local/in-memory, NOT in Supabase, since it's static build-time data, 
     not user data.
   - `filter_candidates(library, section_type, vibe, js_allowed=True) -> list[dict]`: 
     filters by section_type match, vibe in vibe_tags, and js_dependency constraint.

2. `models.py` — Pydantic models
   - `PageBrief`: product_description, campaign_goal, design_vibe, cta_focus, 
     ab_test (bool), raw_ad_content (optional)
   - `BrandKit`: primary_color, secondary_color, text_color, logo_url, font_heading, 
     font_body (all optional)
   - `SectionSelection`: section_type, template_file, values (dict)
   - `PageState`: brief, brand_kit, sections (list of SectionSelection), meta (dict), 
     flags (list)
   - `EditRequest`: page_id, edit_instruction, target_section (optional)

3. `agents.py` — Kimi API agent calls
   Set up the OpenAI client pointed at Kimi K2.7 as described above.
   
   a) `run_copywriter(brief: PageBrief) -> dict`
      System prompt: direct-response copywriter, given the brief, generate headline, 
      subheadline, body copy per section type needed (hero, features, testimonial, 
      pricing), CTA button text. If brief.ab_test is True, generate a second 
      "variant_b" set varying only headline and CTA copy. Return structured JSON only.

   b) `run_designer(brief: PageBrief, copy: dict, brand_kit: BrandKit | None, 
      library: list[dict]) -> list[SectionSelection]`
      - For each required section_type (hero, features, testimonial, pricing), 
        call filter_candidates() to get options matching brief.design_vibe.
      - Pass the filtered candidates (metadata only, NOT full html) plus the copy 
        content to Kimi, asking it to pick the best template_file per section and 
        map copy values + brand_kit colors (or generate a palette if no brand_kit) 
        into the token slots.
      - Return a list of SectionSelection objects.
      - IMPORTANT: the model should never generate raw HTML — only select a 
        template_file from the given candidates and provide token values.

   c) `run_compliance_review(sections: list[SectionSelection], brief: PageBrief) -> dict`
      System prompt: review copy values for ad-policy risk language (guarantees, 
      medical claims, misleading urgency), suggest meta title/description tags 
      for the page based on brief.product_description. Return JSON: 
      {"flags": [...], "meta_title": "...", "meta_description": "..."}

4. `renderer.py` — Jinja2 assembly
   - `render_section(section: SectionSelection, library_path: str) -> str`: 
     loads the matching html_template file, renders it via Jinja2 Template with 
     section.values as context.
   - `assemble_page(sections: list[SectionSelection], meta: dict, 
     pixel_ids: dict | None, library_path: str) -> str`: renders all sections in 
     order (nav, hero, features, testimonial, pricing, cta, footer — skip any not 
     yet in the library), wraps in a full HTML page shell with:
     - <title> and <meta description> from the meta dict
     - Tailwind CDN script tag
     - Conditionally, Alpine.js CDN script tag ONLY if any section has 
       js_dependency == "requires_js"
     - Conditionally, Meta Pixel + Google Ads conversion script tags in <head> 
       if pixel_ids provided (write these as fixed boilerplate templates with 
       ID interpolation, not model-generated)

5. `pipeline.py` — Orchestration
   - `generate_landing_page(user_input: dict) -> dict`:
     1. Build PageBrief from user_input (parse dropdowns, prompt text, ad_url if given)
     2. Run copywriter first, then designer (designer needs copy output to pick 
        token values)
     3. Run compliance review on the assembled sections
     4. Call assemble_page() to get final HTML
     5. Insert a new row into Supabase `pages` table via storage.py
     6. Insert the initial row into `page_versions` too
     7. Return {"html": ..., "page_id": ..., "flags": [...]}

6. `storage.py` — Supabase persistence layer
   Use the supabase client from supabase_client.py for all of these:
   - `save_page(state: PageState) -> str`: inserts into `pages` table, returns new 
     page_id (uuid)
   - `load_page(page_id: str) -> PageState`: selects from `pages` by id, 
     deserializes jsonb columns back into Pydantic models
   - `update_page(page_id: str, state: PageState)`: updates the `pages` row 
     (sections, brand_kit, meta, flags), also updates updated_at
   - `save_version(page_id: str, state: PageState, html: str)`: inserts a new row 
     into `page_versions` — always insert, never update, so history is preserved
   - `get_versions(page_id: str) -> list[dict]`: selects all page_versions rows 
     for a page_id, ordered by created_at desc
   - `get_version(version_id: str) -> dict`: selects a single version row by id
   - Wrap all Supabase calls in try/except and raise clear custom exceptions 
     (e.g. PageNotFoundError) so FastAPI endpoints can return proper HTTP status codes

7. `editing.py` — Chat-based edit flow
   - `classify_edit_intent(instruction: str) -> dict`: cheap Kimi call, returns 
     {"agent": "copywriter"|"designer", "fields": [...], "section_type": "..."}
   - `apply_edit(page_id: str, edit: EditRequest) -> str`:
     1. Load current PageState via storage.load_page()
     2. Classify the edit intent
     3. Re-run only the relevant agent call with current values + instruction, 
        asking it to return the FULL values dict with only the targeted fields changed
     4. Update the specific SectionSelection.values in PageState
     5. Re-run assemble_page() to get new HTML
     6. storage.save_version() to log the pre-edit state, THEN storage.update_page() 
        with the new state
     7. Return new HTML

8. `main.py` — FastAPI app
   Endpoints:
   - `POST /generate` — takes user_input (prompt/ad_url + dropdowns + ab_test flag + 
     optional brand_kit), calls generate_landing_page(), returns html + page_id
   - `POST /edit` — takes EditRequest, calls apply_edit(), returns updated html
   - `GET /page/{page_id}` — loads PageState from Supabase, returns state + rendered html
   - `GET /page/{page_id}/versions` — returns version history from Supabase
   - `POST /page/{page_id}/revert/{version_id}` — loads a specific version's state, 
     re-renders it, calls update_page() to make it current, saves a new version 
     entry marking the revert
   - Return 404 via FastAPI HTTPException when PageNotFoundError is raised

REQUIREMENTS FOR ALL KIMI API CALLS:
- Use response_format={"type": "json_object"} on every call
- Wrap every call in try/except, validate response against the expected Pydantic 
  schema before using it; on validation failure, retry once with a reminder message 
  appended, then raise a clear error if it fails twice
- Use temperature 0.7 for copywriter (creative), 0.4-0.6 for designer (selection task, 
  less creative needed), 0.2 for compliance review (accuracy-focused)
